# 10. Evaluación e Identificación del Stack Tecnológico - EcoLogística Lima

**Proyecto:** EcoLogística Lima - Optimizador de Rutas Sostenibles para DistriRápido S.A.C.
**Versión:** V_1_0_0
**Fecha:** 04 de septiembre de 2026
**Restricción tecnológica base:** Tecnologías de código abierto (RES-06)

---

## 1. Objetivo

Evaluar rigurosamente al menos 3 alternativas de stack tecnológico mediante criterios multidimensionales para seleccionar la combinación que maximice escalabilidad, mantenibilidad, eficiencia energética y alineación con el perfil del equipo y el presupuesto (S/ 500,000 MVP + S/ 120,000/año operación), en el contexto operativo de Lima Metropolitana (conectividad 2G/3G, 1,000 pedidos/día, metaheurística Green VRPTW).

---

## 2. Alternativas Evaluadas

*   **Alternativa 1 - MERN:** Node.js + Express + React + MongoDB (+ Mongoose)
*   **Alternativa 2 - Python / FastAPI + React + PostgreSQL (Propuesta Base)** 
*   **Alternativa 3 - Java Spring Boot + Angular + PostgreSQL**

Todas cumplen RES-06 (open source) y permiten Leaflet/OpenStreetMap (licencia BSD) o Google Maps API.

## 4. Análisis Detallado por Alternativa

### Alternativa 1 - MERN
**Ventajas:** Onboarding rápido, un solo lenguaje, gran pool de devs en Lima, React Native facilita app móvil futura.
**Desventajas:** Inadecuada para Green VRPTW sin servicio externo; MongoDB no óptimo para relaciones complejas (pedidos-vehículos-conductores-rutas) y geoespacial avanzado; eficiencia energética media; riesgo de bloqueo de event loop en optimización.
**Costo estimado MVP (6 meses, 4 devs):** S/ 380,000 (infra USD 450/mes) - dentro de presupuesto pero con deuda técnica algorítmica.

### Alternativa 2 - Python / FastAPI + React + PostgreSQL + PostGIS + Redis
**Ventajas:** Mejor adecuación al dominio (VRPTW + Green VRP), librerías científicas optimizadas en C, FastAPI asíncrono y liviano, PostGIS para geodatos Lima, generación automática de OpenAPI, bajo consumo (eco-design), comunidad data science en Perú en crecimiento.
**Desventajas:** Equipo debe dominar dos lenguajes (Python + JS/React); requiere gestión de workers para metaheurística (Celery + Redis).
**Costo estimado MVP:** S/ 340,000 (infra USD 280-350/mes) - **más económico**, deja margen para iteración 4 y compensación de carbono. Operación anual ~S/ 95,000 vs. S/ 120,000 presupuestado.

### Alternativa 3 - Java Spring Boot + Angular + PostgreSQL
**Ventajas:** Robustez enterprise, OptaPlanner, tipado fuerte, Angular con arquitectura opinada, ideal para escalar a 50 vehículos y 1,000 pedidos con equipo grande.
**Desventajas:** Curva alta, mayor costo infra (JVM), warm-up, desarrollo más lento (verbosidad 2x), menor agilidad para MVP de 14 semanas, costo dev Java senior en Lima más alto (S/ 45-60/h).
**Costo estimado MVP:** S/ 460,000 (infra USD 600/mes) - cercano al límite S/ 500,000, poco margen para imprevistos.

## 5. Justificación Técnica Formal (Decisión del Equipo)

### Declaración Formal de Selección

> **El equipo selecciona por unanimidad la Alternativa 2: Python (FastAPI) + React + PostgreSQL (PostGIS) + Redis + Celery, con Leaflet/OpenStreetMap como capa de mapas base (con fallback a Google Maps API si el cliente financia).**

### Sustentación

1.  **Alineación con el dominio Green VRPTW:** El núcleo del sistema es la metaheurística que minimiza distancia, combustible, CO₂ y penalizaciones por ventanas de tiempo. Python posee el ecosistema más maduro y eficiente (OR-Tools, DEAP, ACO) con implementaciones en C que garantizan el cumplimiento de RNF-001 (≤45s para 150 pedidos/15 vehículos y ≤30s para re-optimización), validado en benchmarks internos. Ninguna otra alternativa ofrece esta ventaja sin incrustar un microservicio Python adicional, lo que desvirtúa la pureza del stack MERN o Java.

2.  **Escalabilidad y costo operativo:** FastAPI asíncrono (ASGI, Uvicorn) ofrece throughput comparable a Node con menor huella de memoria (~200 MB vs. ~500 MB JVM), permitiendo autoscaling horizontal económico en Kubernetes (HPA 3-20 pods) y cumpliendo RES-05 (operación anual S/ 120,000). El ahorro estimado de ~S/ 25,000/año se reinvierte en créditos de reforestación (Árboles para Lima). PostgreSQL con PostGIS es insustituible para datos georreferenciados de Lima (bounding box, vías pavimentadas/no pavimentadas, zonas sensibles) y su costo es inferior a MongoDB Atlas a escala.

3.  **Eficiencia energética y sostenibilidad (Eco-Design):** Conforme a Green Software y RES-02 (cero carbono neto a 3 años), la Alternativa 2 presenta la mejor eficiencia energética (SCI ≤0.5 kWh/1k optimizaciones) por su bajo consumo RAM, queries indexadas (≤200ms P95) y transferencia comprimida (≤300KB payload inicial). La selección de región cloud con energía 100% renovable (ej. AWS sa-east-1 con compromiso renovable o GCP) y la optimización de CPU cycles son coherentes con el propósito del proyecto: el sistema no debe generar más CO₂ del que ahorra.

4.  **Perfil del equipo y mantenibilidad:** El equipo posee formación en Python (cursos de algoritmos y ciencia de datos) y React (frontend moderno), reduciendo la curva de aprendizaje a media. FastAPI genera OpenAPI 3.0 automáticamente, facilitando RNF-007 (documentación 100% y cobertura ≥70% con Pytest/Jest) y onboarding de nuevos mantenedores. React con Vite y TypeScript opcional asegura WCAG 2.1 AA y responsive 2G/3G (RES-06).

5.  **Riesgos mitigados:** La necesidad de un worker para la metaheurística (Celery + Redis) se gestiona como contenedor independiente, desacoplando la API del cómputo pesado y garantizando disponibilidad (RNF-003, RTO ≤60s). La validación W3C y compatibilidad con Chrome 90+ y móviles de gama baja (BrowserStack) se asegura con React.

**Conclusión:** La Alternativa 2 maximiza el valor entregado por sol invertido, cumple todos los RNF críticos, respeta las restricciones locales de Lima (conectividad, costos, normativa) y sostiene la promesa ambiental del proyecto. Las alternativas 1 y 3 se descartan por inadecuación algorítmica y costo/verbosidad, respectivamente.
